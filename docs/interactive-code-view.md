## 用户看到什么

**CL-VIEW-01 · 一次下发的参数与结果。** 从一个 C 入口函数进入。顶层显示这次下发的实参、对应入口字段和流程出口，沿途只露出影响业务的寄存器、静态注册表和运行时已注册状态。资源节点显示这次相关的读、写或注册，能取到值时展示读出值、尝试写入值或注册项。点开任意参数或状态节点，沿「输入字段 → 转换 → 查表键或分支条件 → 寄存器或注册状态」追到具体 C 表达式，看到分支为什么选中、后续如何消费该值、哪里还缺证据。

**CL-VIEW-02 · 给前置状态提供两种入口。** 这里的“表”指前置流程注册进去、后续流程会查询或分派的状态，例如路由项、实例注册和回调绑定。它可能来自静态表，也可能在初始化或运行过程中写入。提供两种方式构造本次初始状态：

- **接口下发。** 走已有 C 配置或注册入口，展示入参经校验、转换后落到哪个已注册对象，再运行或查看目标请求。
- **打桩注入。** 在隔离测试场景按指定键和字段放入等效的注册状态，跳到目标请求；界面标出注入点、注入值和跳过的前置步骤。若配置流程还会建立依赖的对象、同步条件或设备状态，场景应明确哪些已补齐、哪些仍未知。单次场景可重置初始状态，便于比较两条路径。

**CL-VIEW-03 · 以调用关系为阅读和操作入口。** 选择入口后，函数节点默认折叠，只显示名字、作用以及关键状态交接。可以用调用树顺着一条链路读，也可以用上下左右布局的流程图看分派、汇合、异步边界和共享资源。点击函数节点就地展开对应 C 实现和本次相关的条件、数据与子调用，收起后回到原位置。共享子函数可复用同一源码定位，递归和循环显示回边。函数实现的变更也是目标交互：可从节点进入对应实现位置。图内编辑并应用源码、跳转现有编辑器，以及仅在打桩场景替换实现，是后续需分别评估的操作；三者影响的对象不同。

## C 源码和一次执行的关系

- 调用边、类型、分支表达式、字段和资源访问从选定源码版本与构建变体提取，节点能回到文件与行号。用户提交参数、选择入口或打桩时，改变的是本次场景的输入和状态。源码变更后重新核对受影响节点及关系。
- C 源码可以说明有哪些分支和写点。给定参数与已知状态时，可以显示推导出的候选路径和预期写值。展示本次实际经过的分支和寄存器写入，需要对应 C 构建的执行或观测证据。模拟写入、实际发出的写操作和硬件读回各自显示来源；缺输入或观测时标未知。
- 现有 [04 的源码与关系查询](implementation-contract.md)可作为静态骨架的候选底座。带具体值的路径、接口调用、状态注入和源码写回分别有各自的验证前提。实际设备下发、隔离执行、源码修改分别遵循对应的执行与写入边界。

## 用一个场景检验构想

以通信驱动发送为例，选一处查注册表后写寄存器的入口。顶层能看到这次请求的 `channel_id`、匹配的已注册表项和候选寄存器写。展开查表函数可见实参如何组成查表键、命中或未命中走了哪个分支；展开提交函数可见字段如何组成写值。用同一请求对比接口注册和打桩注入两种初始状态，证据齐备时核对关键分支和目标写点；删掉注册项时能解释失败发生在哪。示例符号为构想占位，真实项目名称和语义需查源码。

后续集中确认两项高层选择：视图是否需要连接真实设备下发，函数节点是否需要在图内编辑并写回源码。前者决定观测能力与执行边界，后者决定是否要提供差异预览和变更后的图刷新。调用树与流程图的具体布局留给原型验证。现有首版入口与排期按已确认的产品基线记录。
