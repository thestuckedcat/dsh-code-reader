# 分层阅读与函数定位（CL-007-D1..D3 / CL-PF-02/03 补充）

当用户问“这个函数是干什么的/它会怎么走”时，**先用一句话回答业务作用，再给围绕该函数的局部地图**，
而不是直接堆调用链。顺序固定为四层；每层只取当前问题需要的证据，缺证据就标未知。

## 1. 四层顺序（默认）

| 层 | 回答什么 | 工具/视图 | 关键要求 |
|---|---|---|---|
| 1 业务总框架 | 谁和谁通信、本流程解决什么问题、从哪里进入、到哪里完成 | `code_overview`（组件/仓库边界/接口候选）、工作台端到端图与资源关系图 | 先给一句话定位；画出用户态/UAPI/内核态/设备边界与开始→收发→完成→通知位置；保留 unknown |
| 2 文件与函数职责 | 主体流程分布在哪些文件、每个文件有哪些函数、当前函数落在哪一段 | `view.fileTree`/文件视图、`view.tree`/文字树、`code_source` 有界读取 | 用“文件 → 主要函数 → 职责 → 关键调用”表；标出当前函数涉及的入口、完成、状态更新或设备交互 |
| 3 关键数据与状态 | 目标函数读写哪些关键结构体/字段/软表/硬件资源 | `view.coupling`（writers/readers + exact/may/unknown）、`view.getEntry` 的 resources | 突出目标函数和它的上下游；区分 exact 编译器字段访问与 may 候选；软表/寄存器/设备内存标明谁读谁写、是否缺设备文档 |
| 4 实现证据 | 为什么这样执行、何时完成、失败谁负责、异步/中断在哪 | `code_source` 证据行号、`view.endToEnd` 判断菱形/异常边、observed 时序 | 展开 guard/锁/等待/完成路径；失败返回与资源释放；IRQ/workqueue/定时器是异步完成点还是普通调用；每个结论带 evidence/文件行号 |

一句话定位之后，默认展开第 2–3 层，按需到第 4 层；用户明确要细节时展开 1–2 个关键点，不做全图漫游。

## 2. 当前函数定位步骤

1. 若还没选入口：`view.listEntries` 找候选（按名称/仓库/角色），或 `code_source find` 定位符号。
2. 选中后先看 `view.getEntry`：文件、行号、签名、调用者/被调用者、资源摘要；再用 `code_overview`
   把它放回组件/仓库/接口候选，给出一句业务定位。
3. 用 `view.coupling` 找该函数参与的软表/字段/硬件资源读写；`view.endToEnd` 找它所在的判断/异常路径。
4. 需要“谁调用它/它调用谁到哪结束”时用 `code_path path` 取一条有界路径，再对关键边逐条 `code_source`
   读源码；跨仓用 `code_path relation` 的 binding 候选（最多 may）。
5. 业务图/组件图与局部图分开：业务图回答“在整体流程的哪里”，局部图回答“这一步怎么写/何时完成”；
   两者通过当前入口/Selection 关联，不把局部图当业务图。

## 3. 输出模板（短）

- 一句话：`<函数> 位于 <用户态/内核/设备边界>，负责 <做什么>，从 <入口> 到 <完成/通知>`。
- 文件与函数：3–6 行 `文件 → 主要函数 → 职责`。
- 关键数据：字段/软表/寄存器/设备内存的读写方，标 exact/may/unknown。
- 证据与未知：带文件:行号或 evidence id；缺 build/ABI/设备文档时写 unknown，不猜。

## 4. 边界

- 静态证据不证明运行时必达、硬件完成或线程重叠；observed 时序只证明“一次执行/导入台账中观察到”。
- 字段访问 exact 只说明该编译上下文解析到该对象；软表/硬件资源映射缺设备文档时为 unknown。
- IRQ/workqueue/异步完成点要有 observed 或明确源码证据才展开；无证据只列候选。
- skill 可以调整解释顺序/长度；不能把 may/unknown 说成 exact，不能伪造运行观测或设备行为。
